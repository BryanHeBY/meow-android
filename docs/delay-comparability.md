# Delay comparability at Android 2cd388a

This audit uses the Android tree at `2cd388a8980abae3a07b2ca4067e84c210806049` and its `vendor/meow-rs` gitlink `4954a8d6f9d3ac602d6d5e0e22433ac892cc390f`. The latter was available as a local Git object. No official Meta/mihomo source checkout was available for an independent comparison; comments in meow-rs describing mihomo are not verification of official behavior. No real profile, remote endpoint, device, or VPN was used.

## Configuration path

Android's `engine::strip_and_inject` retains `unified-delay`; meow-config deserializes it into `RawConfig.unified_delay`. At this pin, meow-proxy's process-wide flag defaults to false and meow-app applies `config.raw.unified_delay.unwrap_or(false)` on load. Android previously did not apply it at startup. Android now applies the same value before routing and scheduled health checks; applying false on every start also clears a previous profile's true value in the same process. This is a setting of an atomic flag, not a probe. The core API's config rebuild also applies this flag (`crates/meow-api/src/routes.rs`). The fix depends on the pinned core's `RawConfig` field and `meow_proxy::health::set_unified_delay`; no core dependency change is required. Other revisions must be checked for those APIs and their semantics.

## What is measured

* The group screen's manual test calls `GET /proxies/{member}/delay` with the group's nonblank `testUrl`, otherwise `https://www.gstatic.com/generate_204`, and `timeout=8000` ms per member. Proxy detail's TCP test uses the group URL when supplied, otherwise the same default and timeout. These are HTTP GETs to the local controller; the controller's method is distinct from the probe's method below.
* The pinned core's probe dials the selected adapter, including target TLS for HTTPS. With unified-delay false it sends one HTTP/1.1 GET and times from before dial through response status. With true it sends HEAD twice on one connection, timing the second exchange after reading the first response head. If the second exchange fails or reaches the common deadline, it falls back to the full first measurement and checks the first response status; otherwise it checks the second status. Default acceptance is 2xx. The timeout covers the overall probe, not a separate full budget for each request. Times are integer milliseconds, successful values clamped to 1..65535.
* Manual group tests do not call the group endpoint: they unpin URLTest/Fallback groups, probe distinct members with at most eight in flight, then additionally probe the URLTest group to prompt selection. `testProxyDelay` retries a 503 once after 500 ms; each attempt can record history. A 504 is not retried. These existing extra probes remain; the config fix introduces none. Manual group and detail calls do not pass a group's expected-status, while individual provider-node checks pass the provider's expected-status when configured.
* `GET /group/{name}/delay` is a separate API: it uses one batch deadline, returns successful members only and returns 504 if none succeed. The Android API wrapper defaults that call to 60000 ms. Provider-wide manual health checks use the provider's configured URL, timeout and expected-status; a missing/empty URL yields 204 without probes. A provider node test uses the configured URL or the Android default, 8000 ms, and optional expected-status; it does not use the single-proxy 503 retry. Configured group periodic checks use a 5000 ms core timeout and default URL above; default interval is 300 seconds and `interval: 0` disables them. Provider health-check timeout defaults to 5000 ms and a missing URL does not probe. These schedules are pre-existing and are not made equivalent by the startup fix.
* The detail page's UDP latency test is a different operation: it times a UDP relay and DNS A query for `www.gstatic.com` to `1.1.1.1:53` and then `8.8.8.8:53`, alternating on one-second retransmits, with a five-second total budget. It is not the HTTP URL test and does not write that delay history.

## Display and failures

The pinned core records a positive result or zero for a failed completed URL probe in a node's shared health history, without separating URLs or modes. The group screen uses the latest history entry, temporarily overlaid by in-flight manual results: empty is untested, positive is milliseconds, zero is displayed as timeout even when the cause was another failure. A core timeout returns 504 and a transport or status error returns 503. The detail screen distinguishes 504 timeout from other HTTP failures; a nonpositive returned delay is also treated as timeout. The provider screen uses the API's `delay` if present, else a positive last history value, while its timeout flag comes from the last history entry; the badge displays a positive `delay` before its timeout flag. At this core pin `delay` is emitted only when the *latest* recorded delay is positive, not a separately retained last success. Request failures on provider-node tests are displayed as timeout, and a client-side failure need not imply that the engine recorded zero.

The local Rust regression drives Android's config transformation and setting, then explicitly runs two probes against one in-memory synthetic adapter and `http://probe.invalid/generate_204` (no DNS or sockets). It delays the first response on each connection and checks GET versus two HEADs and cold-versus-warm timing. It checks false, true, and reset on an absent setting. This controlled response delay illustrates what the timers include; it does not model actual proxy handshakes, TLS, routing, mobile conditions, an official mihomo build, or a physical handset comparison. Run with one job: `cargo test --offline --locked --no-default-features -j 1 --lib engine::tests::unified_delay_profile_controls_cold_and_warm_probes_and_resets` from `core/src/main/rust/meow-android-ffi`, with the pinned submodule initialized and cached dependencies available.
